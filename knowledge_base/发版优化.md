# PrismaX 发版流程优化方案

> 文档状态：Proposal
>
> 适用仓库：`app-prismax-rp`（前端）、`app-prismax-rp-backend`（后端）
>
> 团队规模：Dev 2 人、QA 1 人；QA 担任 Production Approver
>
> 最后更新：2026-07-15

## 1. 目标

本方案解决的不是“由谁点击 Deploy”这一单点问题，而是建立一条可追溯、可阻断、可回滚的生产发布链路：

1. Dev 不能直接向 `main` 推送代码，也不能绕过审批发布 Production。
2. 只有经过 Beta 验证且被明确列入本次发布范围的代码，才能进入 `main`。
3. 代码进入 `main` 后不会自动部署 Production，仍需 QA 审批生产构建。
4. 每次发布必须能回答：发布了哪些需求、前后端分别是哪一个 commit、使用了哪组镜像、谁批准、何时上线、如何回滚。
5. 保留小团队需要的轻量和效率，不引入复杂、长期维护成本高的流程。

## 2. 当前流程与仓库核对结果

### 2.1 当前已知流程

```text
feature branch
    ↓ Dev 合入
testing
    ↓ 自动/手动部署
Beta 环境
    ↓ QA 验证
main
    ↓ Dev 部署
Production 环境
```

当前缺口是：QA 的 Beta 测试结论没有形成强制发布门禁，Dev 仍可能直接更新 `main` 或直接触发 Production 部署。

### 2.2 2026-07-15 本地仓库核对结果

| 检查项 | 前端 `app-prismax-rp` | 后端 `app-prismax-rp-backend` | 风险/说明 |
| --- | --- | --- | --- |
| `origin/main` | `bda1835` | `1863296` | 两个仓库独立发布，必须记录两边 SHA |
| `origin/testing` | 比 `main` 多 1 个 commit | 与 `main` 已分叉：`main` 独有 8、`testing` 独有 43 | 后端当前不能把 `testing` 无检查地直接覆盖或快进到 `main` |
| CI/CD 文件 | `cloudbuild.yaml` | `cloudbuild.yaml` | 仓库内没有 GitHub Actions workflow |
| 前端镜像 | 固定标签 `gcr.io/thepinai/app-prismax-rp` | — | 标签会被后续构建覆盖，难以确认 Production 对应的 commit |
| 后端镜像 | 同时生成 `$COMMIT_SHA` 和 `latest`，部署 `$COMMIT_SHA` | 6 个 Cloud Run 服务一起构建和部署 | 后端可追溯性较好，但任一小改动都会重新发布 6 个服务，回归面较大 |
| 部署平台 | Google Cloud Build + Cloud Run | Google Cloud Build + Cloud Run | 审批优先复用 Cloud Build，不必先迁移 CI/CD 平台 |
| 历史更新迹象 | 本地 remote reflog 在 2026-07-14 记录过 `origin/main` forced-update | 2026-06-01、2026-06-21 记录过 forced-update | 表明至少历史上存在重写 `main` 的可能，需禁止 force push |

说明：仓库代码只能看到 `cloudbuild.yaml`，看不到 Google Cloud Console 中 Trigger 的分支条件、替换变量、审批开关和 IAM，也无法从本地确认 GitHub Ruleset/Branch Protection 当前是否启用。因此这些远端设置必须按第 13 节逐项核验，不能把“代码里没写”理解为“一定没有配置”。

### 2.3 当前 `cloudbuild.yaml` 的具体风险

1. 前端镜像没有 `$COMMIT_SHA`、版本号或 digest，重新构建后同一镜像名可能指向不同内容。
2. 后端虽然按 `$COMMIT_SHA` 部署，但仍推送可移动的 `latest` 标签；生产发布记录应使用 commit tag/digest，不使用 `latest`。
3. 当前构建和部署在同一个 Cloud Build 文件中，无法天然实现“Beta 验证过的同一个制品直接晋级 Production”。
4. 后端单次构建会部署 User Management、Teleop、Data Pipeline、Data Worker、Hex、Forum 六个服务；任意模块变化都可能扩大部署和回归范围。
5. 前端 Cloud Run Region 是 `us-west2`，后端是 `us-west1`。这不一定是问题，但回滚命令和监控页面必须按服务实际 Region 操作。
6. 仅通过 `main` 的代码审批准入，不能阻止有 GCP 部署权限的人绕过 GitHub 直接发布，因此 GitHub 和 GCP 两侧都需要权限控制。

## 3. 主流发布流程对比

| 模式 | 核心方式 | 优点 | 缺点 | 对 PrismaX 的适用性 |
| --- | --- | --- | --- | --- |
| GitHub Flow | 短生命周期 feature branch，经 PR 合入主干并持续部署 | 简单、交付快 | 如果 `main` 自动上线，对测试门禁和自动化要求高 | 部分适用；保留短分支和 PR，但 Production 不能无审批自动发布 |
| Git Flow | `develop`、`release`、`hotfix`、`main` 多类长期分支 | 发布边界清晰 | 分支多、合并成本高，容易产生长期分叉 | 不建议完整采用，小团队维护成本过高 |
| Trunk-Based + Feature Flag | 高频合入主干，未完成能力通过开关隐藏 | 分支分叉少，发布频率高 | 依赖成熟 CI、监控和 Feature Flag 治理 | 可作为长期方向，暂不作为第一阶段前提 |
| Release Branch | 从稳定基线创建短期 `release/*`，只纳入批准内容 | 可控制部分需求发布，适合集中发版 | 需要管理 cherry-pick 和重复验证 | 适合当前 `testing` 可能混有多个需求的情况 |
| Environment Approval | 代码合入后，部署任务必须由指定 Approver 放行 | 真正控制“是否上线”，审批有审计记录 | 需要正确的 CI/CD 权限和防绕过设置 | 强烈建议，QA 作为 Production Approver |

推荐采用轻量混合模式：

```text
GitHub Flow 的短 feature branch
        +
testing / Beta 集成验证
        +
必要时使用短期 release branch
        +
main Release PR 审批
        +
Cloud Build Production Approval
```

参考资料：

- [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)
- [GitHub Protected Branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- [GitHub Rulesets 可用规则](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- [Cloud Build 人工审批](https://cloud.google.com/build/docs/securing-builds/gate-builds-on-approval)
- [Cloud Run 回滚与流量迁移](https://cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)

## 4. 推荐目标流程

### 4.1 总流程

```text
Dev: feature/PRIS-xxx
        │
        │ PR + CI + Dev Review
        ▼
testing ───────────────► 自动部署 Beta
                              │
                              │ QA 功能/回归验证
                              ▼
                      QA 标记 Ready for Release
                              │
        ┌─────────────────────┴─────────────────────┐
        │ 本次全部发布                              │ 只发布部分需求
        ▼                                           ▼
testing → main Release PR             main → release/<version>
                                            cherry-pick 已批准提交
                                            部署 Beta-RC 并重新验证
        └─────────────────────┬─────────────────────┘
                              │ QA 审批 Release PR
                              ▼
                            main
                              │ 创建受保护版本 Tag
                              ▼
                   Production Cloud Build Pending
                              │
                              │ QA 审批部署
                              ▼
                         Production
                              │
                              ▼
                     QA Smoke Test + 监控
```

### 4.2 两层 QA 门禁的含义

| 门禁 | QA 审批对象 | QA 主要确认内容 | 审批后发生什么 |
| --- | --- | --- | --- |
| Gate 1：Release PR | `testing/release → main` 的代码和发布清单 | 发布范围、测试结果、已知问题、迁移/配置、回滚方案 | 允许代码进入 `main`，但不等于已经上线 |
| Gate 2：Production Build | 指定 Tag/SHA 对应的 Cloud Build | Tag/SHA 与测试记录一致、时间窗口正确、监控与回滚人员在线 | Cloud Build 才开始部署 Production |

为什么需要两层：PR Approval 保护的是生产代码分支，Cloud Build Approval 保护的是生产环境。只配置其中一层都会留下绕过路径。

## 5. 分支与环境规则

| 分支/Tag | 用途 | 部署环境 | 谁可创建/更新 | 生命周期 |
| --- | --- | --- | --- | --- |
| `feature/PRIS-xxx-description` | 单个需求开发 | 无或临时 Preview | Dev | 合入后删除 |
| `hotfix/PRIS-xxx-description` | 线上紧急修复 | Beta-RC 后 Production | Dev | 发布后删除 |
| `testing` | 多需求集成测试 | Beta | 仅通过 PR 合入 | 长期 |
| `release/YYYY.MM.DD.N` | 本次部分需求的候选版本 | Beta-RC | 仅通过 PR/批准的 cherry-pick | 发布后保留短期，再删除 |
| `main` | 当前生产代码基线 | 不因普通 push 自动上线 | 仅通过 Release/Hotfix PR | 长期、强保护 |
| `vYYYY.MM.DD.N` | 不可变发布版本 | Production | 发布负责人创建，QA 放行部署 | 永久保留、禁止移动 |

### 5.1 默认路径：`testing → main`

只有同时满足以下条件时才使用：

- `testing` 中所有尚未发布的需求都已通过 QA；
- 没有需要暂缓上线的功能；
- 前后端兼容性和配置已一起验证；
- Release PR 的 diff 与发布清单一致。

### 5.2 部分发布路径：`release/*`

当 `testing` 中混有未完成、未通过或本次不计划发布的需求时：

1. 从最新 `origin/main` 创建 `release/YYYY.MM.DD.N`。
2. 只 cherry-pick 已通过 QA 的独立提交。
3. 将该 release branch 部署到 Beta-RC，而不是假设 cherry-pick 后结果与原 Beta 完全相同。
4. QA 在 Beta-RC 至少重测本次需求、核心 Smoke 和前后端兼容性。
5. 创建 `release/* → main` PR，由 QA 审批。

建议将 feature PR 以 squash 方式合入 `testing`，使“一项需求 = 一个可识别 commit”，降低选择性发布难度。不要直接 cherry-pick 未检查的 merge commit。

## 6. 标准发版 SOP

### 阶段 A：需求开发与进入 Beta

1. Dev 从最新 `testing` 创建 `feature/PRIS-xxx-description`。
2. 开发完成后创建 `feature → testing` PR，PR 必须填写需求链接、影响模块、测试方式、配置/数据库变化和回滚注意事项。
3. 至少 1 名另一位 Dev 完成代码 Review；CI 全部通过后才可合入。
4. 使用 squash merge，合入 commit 标题保留 PRIS 编号。
5. `testing` 的 Cloud Build Trigger 自动部署 Beta，不需要 QA 人工批准。
6. Dev 先完成 Beta 基础自测，再通知 QA，避免把不可测版本交给 QA。

### 阶段 B：QA 验证与准入

QA 对每个需求记录：

- Beta 构建 ID；
- 前端 commit SHA、后端 commit SHA；
- 需求测试结果；
- 影响模块回归结果；
- 未解决问题及其严重级别；
- 结论：`Ready for Release` / `Blocked`。

以下情况不得标记 `Ready for Release`：

- 存在未接受的 P0/P1 缺陷；
- 测试环境与 Production 所需配置不一致且未验证；
- 数据库迁移没有兼容/回滚方案；
- 无法确定实际测试的前后端 SHA；
- 发布后无可执行的 Smoke 或回滚方法。

### 阶段 C：形成 Release Candidate

1. PM 确认业务发布时间和需求范围，QA 确认测试准入。
2. Dev 创建统一 Release 记录，写明两个仓库的精确 SHA；没有变化的仓库也明确写 `No change` 和当前生产 SHA。
3. 如果 `testing` 全部可发布，创建 `testing → main` Release PR；否则按第 5.2 节创建 `release/*` 并重新部署 Beta-RC。
4. Release PR 冻结后，不再追加需求。任何代码变化都会使原 QA Approval 失效并要求重审。
5. 前后端各自创建 Release PR；两边 PR 互相链接，并共用同一个版本号。

### 阶段 D：QA 审批 Release PR

QA 按以下顺序检查：

1. PR diff 只包含发布清单中的内容。
2. PR 顶部显示所有 Required Checks 已通过。
3. 前后端 API、配置和部署顺序匹配。
4. Beta/Beta-RC 中验证的 SHA 与 Release Candidate 一致。
5. 已知问题已由 PM 接受，回滚条件和负责人明确。
6. 满足以上条件后点击 Approve；有问题则 Request changes，不用口头同意代替 GitHub 审批。

Release PR 合入 `main` 后，只代表“具备发布资格”，不得因为 `main` 更新而自动上线。

### 阶段 E：创建版本并请求 Production 部署

1. Release Owner 在 `main` 合入 commit 上创建 annotated tag，例如 `v2026.07.15.1`。
2. 两个仓库使用相同版本号；Release 记录保存两个不同的 commit SHA。
3. Production Trigger 只接受符合 `^v[0-9]{4}\.[0-9]{2}\.[0-9]{2}\.[0-9]+$` 的 Tag。
4. Trigger 必须启用 `Require approval before build executes`，此时状态为 Pending，不应已开始部署。
5. Dev 在发布群/Release 记录中通知 QA，并提供 Build ID、Tag、SHA、计划时间和回滚版本。

### 阶段 F：QA 批准 Production Build

QA 在 Google Cloud Build 中核对：

- 仓库、Tag 和 commit SHA 与 Release 记录一致；
- Build 使用 Production Trigger 和 Production service account；
- 前端和后端的发布顺序正确；
- 当前没有另一个 Production 部署正在执行；
- 发布窗口、监控人员、回滚人员已就绪。

核对通过后点击 Approve；不通过则 Reject 并写明原因。QA 不执行构建命令，实际部署由 Cloud Build service account 完成。

### 阶段 G：部署后验证与关闭

1. Dev 监控 Build、Cloud Run revision、错误日志和关键指标。
2. QA 执行 Production Smoke Test。
3. 前后端均成功且 Smoke 通过后，QA 将 Release 标记为 `Released`。
4. 记录实际部署时间、Cloud Build ID、Cloud Run revision、镜像 digest 和 Smoke 结果。
5. 观察期内出现回滚条件时，立即按第 10 节处理。

## 7. 前后端联合发布规则

前端和后端是两个仓库，但用户看到的是一个产品版本，必须使用一份 Release Manifest：

| 字段 | 示例 |
| --- | --- |
| Release Version | `v2026.07.15.1` |
| Frontend SHA | `app-prismax-rp@<40位SHA>` |
| Backend SHA | `app-prismax-rp-backend@<40位SHA>` |
| Frontend Image Digest | `sha256:<digest>` |
| Backend Image Digests | 六个服务分别记录 `sha256:<digest>` |
| Included PRIS | `PRIS-xxx, PRIS-yyy` |
| Config/Migration | 有/无；执行顺序 |
| Rollback Version | 上一个稳定 Release Manifest |
| QA Approver | GitHub/GCP 用户名 |

发布顺序根据兼容性选择：

- 后端向后兼容：先后端、验证 API，再前端。
- 前端依赖新后端字段：必须先部署后端。
- 破坏性 API 变化：采用 expand-and-contract，先让后端同时兼容旧/新前端，后续版本再删除旧接口。
- 只改一个仓库：另一个仓库在 Manifest 中写 `No change`，禁止留空。

## 8. 制品与 Cloud Build 改造建议

### 8.1 第一阶段：最小改造

1. 保留现有 Google Cloud Build + Cloud Run。
2. 为 Beta 和 Production 使用不同 Trigger、不同 service account、不同 substitutions。
3. Beta Trigger：监听 `testing`，无需人工审批，只能部署 Beta 服务名。
4. Production Trigger：只监听受保护版本 Tag，必须人工审批，只能部署 Production 服务名。
5. QA 获得 `roles/cloudbuild.builds.approver`；Dev 不授予该角色。
6. Dev 不应拥有修改 Production Trigger、冒用 Production service account 或直接更新 Production Cloud Run 的权限。
7. 前端镜像立即增加 `$COMMIT_SHA` 标签，Production 不再部署无版本标签。

### 8.2 第二阶段：Build once, promote the same artifact

将现在“构建 + 部署”的单一配置拆为：

```text
build.yaml
  └─ 测试、构建镜像、推送 commit SHA、输出 digest

deploy-beta.yaml
  └─ 把上述 digest 部署到 Beta

deploy-prod.yaml
  └─ QA 审批后，把同一个 digest 部署到 Production
```

目标是 Production 使用 QA 已经在 Beta-RC 验证过的同一镜像 digest，而不是审批后重新构建一份“理论上相同”的镜像。镜像 digest 是不可变标识，发布记录应优先记 digest；`latest` 只能用于开发便利，不能作为生产发布依据。

参考：[Artifact Registry 镜像名称与 digest](https://cloud.google.com/artifact-registry/docs/docker/names)。

### 8.3 后端六服务拆分建议

短期可以继续统一发布，但 Release Manifest 必须记录六个 revision。中期建议：

1. 按变更路径触发对应服务的构建，例如仅 `app_prismax_hex/**` 变化时不重建 Teleop。
2. 每个服务使用独立镜像 SHA/digest 和部署步骤。
3. Release Manifest 标记实际变化/部署的服务。
4. 公共依赖或 `cloudbuild.yaml` 变化时，再执行全服务构建和扩展回归。

## 9. GitHub 保护规则

两个仓库都应配置一致的 Ruleset；优先使用 Ruleset，旧版仓库也可用 Branch Protection 实现等价规则。

### 9.1 `main` 必开项

- Require a pull request before merging。
- Required approvals：1。
- Require review from Code Owners；使用 `CODEOWNERS` 指定 QA/Release Approver。
- Dismiss stale approvals when new commits are pushed。
- Require approval of the most recent reviewable push。
- Require status checks to pass；至少包括 build、unit test、lint/静态检查，后续增加 E2E。
- Require conversation resolution before merging。
- Block force pushes。
- Restrict deletions。
- Do not allow bypassing；管理员也不得日常绕过。
- 限制直接 push，正常路径只允许 GitHub PR merge。

`CODEOWNERS` 设计示例：

```text
# main Release PR 需要 QA/Release Approver 审核；实际团队名按 GitHub Org 配置替换
* @PrismaXAI/release-approvers

# CI/CD 配置同时需要代码维护者和发布审批者关注
/.github/ @PrismaXAI/release-approvers
/cloudbuild.yaml @PrismaXAI/release-approvers
```

注意：普通的“Required approvals = 1”只保证有人批准，不天然保证批准人一定是 QA；必须结合 Code Owner、指定 reviewer 或发布 Ruleset。Production Cloud Build Approval 才是最终环境门禁。

### 9.2 `testing` 建议项

- Require a pull request before merging。
- 至少 1 名另一位 Dev Review；QA 不需要逐个做代码 Review。
- Required status checks 必须通过。
- Block force pushes、Restrict deletions。
- 允许快速迭代，但不允许直接 push 绕过 CI。

### 9.3 Tag 保护

- 创建匹配 `v*` 的 Tag Ruleset。
- 禁止移动、更新或删除已有 Release Tag。
- 只允许 Release Owner 创建 Tag。
- Production Trigger 必须从 Tag 解析并记录完整 commit SHA。

## 10. 回滚与 Hotfix

### 10.1 回滚触发条件

满足任一条件可由 Dev 或 QA 发起回滚，执行不等待新的常规发版审批：

- 核心页面/API 不可用；
- 登录、支付、上传、Teleop、数据处理等主链路出现 P0/P1；
- 错误率、延迟或资源消耗明显超阈值；
- 数据写坏、权限越权、安全或隐私风险；
- 发布后无法在约定观察时间内定位/修复。

### 10.2 Cloud Run 回滚

优先把流量切回上一个已知稳定 revision，而不是现场重新构建旧代码：

```bash
gcloud run services update-traffic <SERVICE> \
  --to-revisions <LAST_STABLE_REVISION>=100 \
  --region <SERVICE_REGION>
```

后端有六个服务，不应机械地全部回滚；根据 Release Manifest 和依赖关系确定受影响服务。如果数据库发生不可逆迁移，仅回滚应用可能造成更严重问题，必须预先采用向后兼容迁移。

回滚完成后：

1. QA 执行核心 Smoke。
2. Release 状态改为 `Rolled Back`，记录原因、revision 和时间。
3. 创建缺陷/事故记录；禁止移动原 Release Tag。
4. 修复后走 Hotfix 流程重新发布新版本号。

### 10.3 Hotfix 流程

```text
main → hotfix/PRIS-xxx
     → Dev Review + CI
     → Beta-RC 验证
     → hotfix → main PR（QA Approval）
     → 新 Tag
     → Production Build（QA Approval）
```

紧急不等于无审计。只有在平台故障导致正常审批系统不可用时才允许 Break-glass；必须由 PM/负责人确认，并在 1 个工作日内补齐 PR、Build、原因和复盘记录。

## 11. 角色与职责（RACI）

| 活动 | Dev | QA / Production Approver | PM | Repo/GCP Admin |
| --- | --- | --- | --- | --- |
| 开发、自测、PR | R/A | I | I | I |
| Code Review | R | C | I | I |
| Beta 部署维护 | R | I | I | C |
| Beta 功能与回归测试 | C | R/A | I | I |
| 确定业务发布范围/窗口 | C | C | R/A | I |
| Release Manifest | R | A | C | I |
| Release PR Approval | C | R/A | I | I |
| 触发 Production Build | R | I | I | I |
| Production Build Approval | I | R/A | I | C |
| 部署监控与技术回滚 | R | C | I | C |
| Production Smoke | C | R/A | I | I |
| Ruleset、Trigger、IAM 维护 | I | C | I | R/A |

`R` = 执行，`A` = 最终负责，`C` = 协作/咨询，`I` = 知会。

### QA 单点风险

QA 只有 1 人，不能把流程设计成 QA 不在线就永久无法处置事故：

- 正常发布：只能由 QA 审批。
- 计划休假：提前指定 1 名经过授权的 Backup Approver，授权有起止时间。
- 紧急回滚：Dev 可执行流量回切，但必须通知 QA/PM 并补记录。
- QA 不能批准自己发起的 Production 部署；生产 Trigger 由 Dev 发起、QA 审批。

### 13.3 当前分支基线治理

在正式启用新流程前，先处理现有历史分叉：

1. 前端检查 `origin/testing` 比 `origin/main` 多出的 commit 是否计划发布。
2. 后端对 `origin/main...origin/testing` 的 8/43 个独有 commits 做一次发布范围审计。
3. 不允许用 force push、`reset --hard` 后强推等方式“对齐”远端分支。
4. 通过一次明确的 Baseline Release PR 合并双方需要保留的代码、解决冲突并跑完整回归。
5. 基线稳定后，再要求所有新改动只通过 PR 流转，避免继续扩大分叉。

## 14. GitHub Environment 的可选方案

如果 GitHub 版本和仓库 Visibility 支持 private repository 的 Environment Required Reviewers，也可以在 GitHub Actions 中使用 `environment: production`，设置 QA 为 Required Reviewer、开启 Prevent self-review，并限制只有受保护 Tag 可部署。

但 GitHub 官方当前说明：Free、Pro、Team 计划的 Required Reviewers 只对 public repository 可用。若 PrismaX 仓库是 private 且计划不支持此功能，应以 Cloud Build Require Approval 为实际生产门禁，不要在文档中假设 GitHub Environment 一定可用。

参考：[GitHub Deployments and Environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)。

## 15. 分阶段实施建议

### P0：立即实施（1～2 天）

1. 保护两个仓库的 `main`、`testing` 和 Release Tag，禁止 direct push/force push。
2. Production Cloud Build Trigger 开启人工审批，QA 获得 Approver，Dev 移除 Approver。
3. 建立 Release Manifest、Release PR 和 Checklist。
4. 前端镜像增加 commit SHA 标签。
5. 对当前前后端分支分叉做 Baseline 审计。

### P1：一周内

1. 补齐前后端 CI Required Checks。
2. 拆分 Beta/Production Trigger 和 service account 权限。
3. 建立 Production Smoke 自动化/半自动化。
4. 演练一次 Reject、一次 Cloud Run rollback。

### P2：后续优化

1. Build once，以镜像 digest 从 Beta-RC 晋级 Production。
2. 后端六服务按目录和依赖进行选择性构建/部署。
3. 增加灰度流量、错误率自动判断和自动回滚。
4. 对未完成能力引入 Feature Flag，逐步减少长期 `testing` 分叉。

## 16. 验收标准

流程改造完成必须实际演练，不能只看设置页面：

1. Dev 直接 push 和 force push `main` 均失败。
2. 未经 QA Approve 的 Release PR 无法合入 `main`。
3. 新 commit 推入已批准 PR 后，旧 Approval 自动失效。
4. 普通 `main` 更新不会直接部署 Production。
5. Production Build 未经 QA 审批保持 Pending；Reject 后不部署。
6. Dev 无法审批自己的 Production Build，也无法绕过 Trigger 直接部署。
7. 发布完成后能从 Release Manifest 追溯到前端、后端、六个后端服务的 revision/digest。
8. 能在约定时间内把一个服务回滚到上一个稳定 Cloud Run revision，并通过 Smoke。

满足以上 8 项后，才可以认为“QA 是 Production Approver”已经由制度要求变成技术上可执行、可审计的发布控制。

## 17. Jira Ticket

### Title

Implement QA-Gated Production Release Process

### Description

Improve the PrismaX release process for both frontend and backend repositories to ensure that only QA-verified changes can be released to Production.

### Requirements

- Protect `main` and `testing`: require PR approval and CI checks; block direct and force pushes.
- Automatically deploy `testing` to Beta for QA verification.
- Require QA approval before merging a Release PR into `main`.
- Trigger Production deployment only from a protected version tag.
- Enable manual QA approval for Production builds in Google Cloud Build.
- Tag frontend and backend images with the commit SHA and record the deployed SHA/image digest for traceability and rollback.
- Ensure Dev users cannot bypass approval or deploy directly to Production.

### Acceptance Criteria

A Production deployment cannot start without QA approval, and each release can be traced to its frontend/backend commits, image digests, approver, and previous stable version.
